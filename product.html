What PandoCore Does

Traditional runtime security tools require you to write detection rules for every threat you want to catch. If you don't write the rule, you miss the attack.

PandoCore takes a different approach. It automatically learns what normal looks like for each workload, then continuously monitors for deviations. When anomalous behavior is detected, it responds with a graduated action chain: alert, then isolate. On a first encounter that reached isolation, detection to containment took about 60 seconds without a human in the loop, measured twice on live infrastructure.

PandoCore is not a replacement for encryption, authentication, a service mesh, observability, secrets management or network policies. It adds a behavioral detection and response layer at runtime, alongside the controls you already run. If one of them fails, a behavioural layer narrows what that failure buys an attacker; it does not cancel it.

Validated Against Real Workloads

The node sensor has been run against production-representative workloads in extended soak runs on GKE. No manual configuration or tuning was performed, and every workload ran with default settings.

Zero false isolations across 3,966 engine-hours of sensors that were permitted to isolate, 1,231 of them on the exact build we ship.

Measured warm and enforcing on the shipping build, across two runs: a 130.4 mCPU p95 with a 106.9 MiB working set over a 24-hour warm window, and 127.3 mCPU with 110.6 MiB over a 34-hour run. The working set held a flat slope in both, so there is no leak to grow into the limit.

Cumulative across two runs rather than one unbroken window, measured on one node per run, against production-representative synthetic workloads rather than customer traffic. A zero bounds the rate rather than being one: at most one false isolation in 1,324 engine-hours, at 95 percent confidence. Profiling is automatic across the 24 workload types these runs covered, spanning web servers, databases, and JIT and interpreted runtimes, with no manual tuning required. These figures are from the node sensor; the earlier per-pod collector's numbers are not carried forward. Those runs measured CPU, memory and false isolations. They are not a measure of detection coverage, and we do not present them as one.

The access it needs, and what it is denied

The sensor runs as a hostPID DaemonSet, as uid 0, with CAP_SYS_PTRACE, reading the node's process namespace read-only. Anything that never executes there is outside what it can see. That is a real privilege, and what bounds it is the grant rather than a promise: its ClusterRole withholds pods: delete, pods: patch and endpoints: get by name. Each sensor watches up to 70 pods per node, and a Prometheus gauge reports any past that.

It will not run on GKE Autopilot or EKS Fargate. Both forbid hostPID, so there is no install path on either. Standard GKE is the configuration this release was validated on.
