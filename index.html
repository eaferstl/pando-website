The Problem

A customer's security questionnaire or your auditor wants to know what watches your Kubernetes workloads at runtime. "Nothing yet" isn't an answer.

They assume someone writes and tunes the rules. If nobody owns that, the box stays unchecked.

Sources: Jobicy and ZipRecruiter US security engineer salary data (2026); ISACA State of Cybersecurity 2025.

A Different Approach

Rule-based runtime security asks you to anticipate the attack and then maintain the rule. PandoCore learns what normal looks like for each of your workloads instead, flags when behavior deviates, and responds within a ceiling you set. On a first encounter that reached isolation, detection to containment took about 60 seconds without a human in the loop. Install the two charts and the workloads already running on each node start learning, with nothing to label.

Measured on GKE: zero false isolations across 3,966 engine-hours of sensors permitted to isolate, 1,231 of them on the build we ship.

An engine is the per-pod detection instance, one pod to one engine. An engine-hour is one hour in which an engine was fully warmed and permitted to isolate; hours spent learning a workload's baseline are excluded, because an engine that is still learning cannot isolate anything.

What You Are Actually Installing

Two Helm charts, controller first. The controller receives evidence and owns delivery; the sensor is a DaemonSet that puts one pod on each node. A sensor installed without a controller will not start, which is deliberate: it would otherwise run with nowhere to send what it found. Nothing is added to your workloads, so there is nothing to label and no pod to restart.

# 1. The controller: receives evidence and owns every outbound destination
helm install pando-controller \
  oci://us-central1-docker.pkg.dev/pandocore-prod/charts/pando-controller \
  --version 2.0.0 \
  --namespace pando-system --create-namespace \
  --set license.key="YOUR_LICENSE_KEY"

# 2. The node sensor: one pod per node
helm install pando-node-sensor \
  oci://us-central1-docker.pkg.dev/pandocore-prod/charts/pando-node-sensor \
  --version 2.0.0 \
  --namespace pando-system \
  --set license.key="YOUR_LICENSE_KEY"

--version is mandatory: an OCI chart installed without it fails rather than resolving to the newest release. Your portal dashboard carries both lines with the key and the current version filled in, and the install guide covers the rest.

The sensor watches the pods on its node by default. A pod opts out with the exact label pandocore.io/protect: "false", and four classes are excluded whatever the configuration says. Each sensor watches up to 70 pods per node; past that, pods get no engine and a Prometheus gauge reports them, because a coverage gap you cannot see is worse than one you can.

The access it needs, and what it is denied

The sensor runs as a hostPID DaemonSet, as uid 0, with CAP_SYS_PTRACE, reading the node's process namespace read-only. That is a real privilege, and it is the reason the previous per-pod design was retired: one process per node sees what it needs without anything running inside your containers.

What bounds it is the grant rather than a promise. The sensor's ClusterRole withholds pods: delete, pods: patch and endpoints: get by name, each with its reason recorded in the chart, so the hardest action available to it is a NetworkPolicy. The cluster-wide secret access that per-namespace integrations need is held by a separate unprivileged component, not by the pod running on every node. The trust center lists the full grant and the failure modes.

It will not run on GKE Autopilot or EKS Fargate. Both forbid hostPID, so there is no install path on either, and we would rather you learn that here than at the end of an install. Standard GKE is the configuration this release was validated on.
